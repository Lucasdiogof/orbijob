# OrbiJob 3.0 — smart discovery, alerts and application follow-up

What 3.0 adds on top of 2.0, how each part works, what protects it and what it does **not** do. Everything below is implemented, covered
by automated tests and (for the database parts) applied to the OrbiJob project. Limits and pending owner actions are listed at the end.

## 1. Saved searches

* **What is saved:** the text, the country (or continent), the professional area and health specialty, the work modes, "published in the last N
  days" and "only with salary" — every filter Explore has. Stored in `saved_searches.query` (JSON, version 2) together with a compiled `match`
  block the database can evaluate (see §2). Searches saved by earlier builds (`{term, country}`) still open.
* **Manage:** *Explore → Save search* (or the entry in the empty-results state), *Saved searches* page (Profile → Saved searches and alerts, the
  "My searches" chip in Explore, the chips on Home): open in Explore, edit (name, alerts, frequency, replace the criteria with what Explore
  shows now), duplicate (a copy starts with alerts off), delete.
* **Limits:** 100 searches per account (database quota), at most 20 with alerts on (cubit), name ≤ 80 characters.
* **Security:** owner-only RLS; the client cannot write the alert cursor or the last-run time (column-level grants + tests).

## 2. Alerts and the notification centre

* **Detection:** `ops.alerts_run()` (pg_cron job `alerts-run`, every hour at minute 53 UTC) looks, per saved search with alerts on and due by its
  frequency (every hour / once a day / once a week), at jobs first stored after the search's cursor. `jobs.first_seen_at` is when OrbiJob first
  stored a job — never the source's publication date.
* **Only valid jobs are announced:** status `open`, verified in the last 72 h, published in the last 60 days (or undated), from a source that is
  `READY`/`CONDITIONAL` **and** redistributable, not hidden by the user, not already announced (same job id, or the same fingerprint under another
  source). A job that closed before the run is never announced.
* **Same rules as the app:** `ops.alert_matches` implements the catalogue query of the app (full-text or substring of title/city, the profession's
  other names, country incl. eligible and remote-anywhere, continent, work modes, area keywords, specialty = area AND narrower words, days, salary).
  A golden file generated by the app (`worker/test/fixtures/v3-specs.golden.json`) and checked on both sides keeps them identical.
* **Idempotent:** unique `(user, job)`, a 15-minute overlap window for late commits, at most 25 per search per pass (the rest on the next pass),
  a person who switched alerts off gets no backlog when switching on, editing a search restarts its cursor.
* **Notification centre:** the bell (badge with the unread count) → *Notifications*: read, mark all as read, dismiss, clear (dismissed rows stay
  stored for the 60-day window so the same job is not announced again), the global switch (`user_preferences.settings.notifications.enabled`), a
  shortcut to the saved searches. The app re-reads on open and every 5 minutes while open. Opening a notification opens the job (or, if it left the
  catalogue, says so and offers the original listing).
* **Housekeeping:** notifications older than 60 days are deleted; at most 300 per user; `ops.alert_runs` keeps 30 days.
* **Switch off:** `scripts/supabase/ops/disable_alerts_cron.sql`. Re-enable: `enable_alerts_cron.sql` (asks for an explicit phrase).

### Push notifications (phone / browser)

Android and iOS push is implemented, deployed and configured (2026-10-13): the Firebase service-account key is stored, OAuth and FCM authorisation were verified against Google, and the scheduled function answers `ok`.

* **Device side:** `firebase_messaging`. After sign-in the app asks for permission (once) and stores its token in `public.push_devices` (migration
  17, owner-only RLS, at most 10 devices per person, the oldest makes room). Before sign-out the row is deleted and the token forgotten, so the next
  account on the same phone starts clean. Tapping a push opens the notification centre. Web and desktop have no push.
* **Configuration (not in Git, the repository is public):** Android reads `app/android/app/google-services.json` (the Google services Gradle plugin
  is applied only when that file exists); iOS takes `FIREBASE_IOS_API_KEY`, `FIREBASE_IOS_APP_ID`, `FIREBASE_SENDER_ID`, `FIREBASE_PROJECT_ID`
  from `--dart-define` (`dart_defines.dev.json`). A build without them simply has no push.
* **Sender:** Edge Function `push-send` (`supabase/functions/push-send`), called every hour at minute 56 by pg_cron (`push-send` job, three
  minutes after the alerts). It uses the internal database connection of the project and only `ops.push_claim` / `ops.push_forget_tokens`: no API
  role gains access to notifications or devices. It claims unsent, unread rows of the last 6 hours, respects the global "notifications" switch,
  sends one FCM v1 message per device in the language of the person (title and company exactly as the listing states), and forgets tokens FCM no
  longer knows. A row is marked even if Google is down, so nobody receives an old burst later; the bell always has it.
* **Secrets:** `PUSH_CRON_SECRET` (function) = `push_cron_secret` (Vault): generated and stored. `FCM_SERVICE_ACCOUNT` (function): stored 2026-10-13.
  Without it the function would answer `not_configured` and touch nothing.
* **Switch off:** `scripts/supabase/ops/disable_push_cron.sql`.

## 3. Recommendations

* **Deterministic and explainable, on the device:** no AI service, no network call beyond the catalogue queries. Candidate jobs come from a handful
  of catalogue searches (the person's profession and skills as terms, their countries, remote jobs); ranking happens locally in `Recommender`.
* **Any profession:** the profession is whatever the headline and the last job titles say ("Enfermeira", "Eletricista", "Accountant"), matched by
  whole phrase, close forms (gender/number), the same profession in another language (`search_synonyms`) and the same professional field.
* **Score = share of the evaluable criteria met** (profession 50, skills 15, place 20, work mode 10, language 10, recency 5). A criterion the profile
  does not provide is not evaluated and cannot lower the score; a profile with nothing to compare gets an invitation to fill it, not random jobs.
* **Preferences versus must-haves:** the profile form has three switches (only my work mode / my countries / my languages). A preference only
  raises a job; a must-have removes a job **only when the listing says the opposite** — a listing that is silent is kept, with a note.
* **Reasons, always:** each recommendation lists what matched (in words) and what is worth checking, plus the standing disclaimer that visas, work
  permits, professional registration and certifications are **not** evaluated. A listing that restricts who may apply only carries a reminder.

## 4. Hide jobs and history

* **Hide / restore:** the ⋮ menu on any card or detail page; an undo appears at once; the *Hidden jobs* page (Profile) restores. Persisted per
  account (`hidden_jobs`, identity `source:externalId`, owner-only RLS, 2000 per account). Hidden jobs are dropped from Explore (the page keeps
  loading when a whole page was hidden), Home and recommendations, and excluded from alerts by the database.
* **Recent searches:** kept on the device only (never sent), separately per account and for "not signed in"; written when a search is submitted
  (not per keystroke) and coalesced into one write; Settings → Search history: switch off (also forgets) and clear.

## 5. Application pipeline

* Stages: **interested**, applied, screening, **interview**, offer, **hired**, rejected, withdrawn, closed (existing rows untouched).
* *Track this job* (⋮ menu) adds a listing as "interested" — nothing is sent and no application date is recorded; opening the in-app browser never
  records anything; the "Did you apply?" prompt records only on confirmation (unchanged).
* The first move to a stage that exists after applying records today as the application date (editable only by moving stages; never overwritten).
* Interview (date + time) and follow-up (day) dates, notes, stage history; the Applications tab shows *Coming up* (next 14 days, overdue flagged),
  a stage filter with counts, and the next date on each card.
* OrbiJob never contacts the employer and never submits or prefills anything on a third-party site.

## 6. Share and compare

* **Share:** title, company and the listing's own link through the system share sheet (copied to the clipboard where sharing is unavailable). No
  tracking parameters; nothing is shared for a job without a web link.
* **Compare:** up to three jobs (⋮ → Add to comparison, a bar above the navigation, *Compare*): a table on wide windows, one block per attribute on
  phones. Only what each listing states: a missing value is "Not stated" — never estimated, defaulted or copied. "Who can apply" comes only from
  the explicit restriction list (a location is not eligibility). Salaries in different currencies or periods are shown as stated, without conversion,
  with a note.

## 7. Engineering and safety

* Migration `20261023000000_v3_searches_alerts.sql` (applied to `rpmlfxwebnlxnwadyvle` on 2026-10-13): idempotent, with a rollback file; no
  SECURITY DEFINER, no function callable by `anon`/`authenticated`, no change to RLS of existing tables, new tables owner-only with column-level grants.
* Tests: SQL on PGlite and on real PostgreSQL 16/17 (privileges, cross-user, matching, dedupe, cap, frequency, pruning, golden parity), repository
  contracts against a fake PostgREST, cubit tests, widget tests, accessibility, the 320 px / 200 % text layout net in en/pt/es for every new screen.
* The alert run was also executed once on the **real catalogue** inside a transaction that was rolled back (nothing stored): 25 notifications for a
  "remote jobs" search on the first pass (capped), the rest on the next, every one open and verified in the last 72 h.
* Quota/storage: database 109 MB of 500 MB (free plan); the new tables hold small rows with per-user caps.

## 8. Not done / needs the owner

* Push on phone or browser (see §2) and local interview reminders.
* On-device validation (Android physical device, iOS) of the new screens; only widget tests, the web release build and the Android emulator work of 2.0
  were available.
* Alerts are as fresh as the discovery workflows: GitHub scheduled runs can be delayed by hours on the free plan.
